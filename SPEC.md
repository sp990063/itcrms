# IT Service Change Request Management System — SPEC

## 1. Project Overview

**Project Name:** IT Change Request Management System (ITCRMS)

**Goal:** A self-hosted internal web application that manages IT service change requests through a multi-stage approval workflow, with role-based access control, email + in-app notifications, per-CR chatrooms with @mentions, and full audit trail.

**Target Users:**
- IT Staff / IT Supervisors / IT Section Heads / IT Directors
- Business User (change requesters) / their Supervisors
- Change Control Committee Members
- System Administrators

**Key Principle:** 100% generated by coding agents (no human developers). All code must be clean, compilable, and deployable on first run.

| Layer | Technology |

| Frontend | Next.js (Pages Router) |

### 3.2 Row Level Security (RLS)

```sql
-- RLS is enabled on all tables
-- Role-based row visibility:

-- IT Staff / Supervisor / Section Head / Director: see all CRs
-- Committee: see CRs in committee review stage
-- User: see only their own submitted CRs

alter table change_requests enable row level security;

create policy "it_roles_full_access"
    on change_requests for all
    using (
        exists (
            select 1 from user_app_roles uar
            join app_roles ar on ar.id = uar.role_id
            where uar.user_id = auth.uid()
            and ar.name in ('it_staff','it_supervisor','it_section_head','it_director','committee_member','admin')
        )
    );

create policy "user_sees_own"
    on change_requests for select
    using (applicant_id = auth.uid());
```

### 3.3 Database Functions (Edge Functions trigger these)

```sql
-- Auto-assign CR number: CR-YYYY-NNNNN
create function next_cr_number() returns text as $$
    select 'CR-' || to_char(now(), 'YYYY') || '-' || lpad(coalesce(
        (select cast(count(*) + 1 as text) from change_requests
         where cr_number like 'CR-' || to_char(now(), 'YYYY') || '-%'),
        '1'), 5, '0');
$$ language sql;

-- Notify via email + in-app
create function notify_users(p_user_ids uuid[], p_cr_id uuid, p_subject text, p_body text, p_type text) returns void as $$
    insert into notifications (user_id, cr_id, subject, body, type)
    select unnest(p_user_ids), p_cr_id, p_subject, p_body, p_type;
$$ language sql;
```

## 4. Workflow State Machine

### 4.1 Approval Routing Logic (determines next required approvals)

```
Step: IT Supervisor Approves Impact Analysis
├── IF: risk_level = 'high' AND (system_tier = 'tier2' OR system_tier = 'tier1h' OR is_internet_facing = true)
│   → Next: Section Head Approve
│   → Next Next: Director Approve
├── ELIF: system_tier = 'tier2' OR is_internet_facing = true
│   → Next: Section Head Approve
├── ELSE: proceed to Cost Estimate
```

### 4.2 State Transitions

```
DRAFT → (User submits) → PENDING_USER_SUPERVISOR
PENDING_USER_SUPERVISOR → (User Supervisor rejects) → REJECTED
PENDING_USER_SUPERVISOR → (User Supervisor approves) → PENDING_IT_PICKUP
PENDING_IT_PICKUP → (IT Staff claims) → PENDING_IT_IMPACT
PENDING_IT_IMPACT → (IT Staff submits Impact Analysis) → PENDING_IT_SUPERVISOR
PENDING_IT_SUPERVISOR → (IT Supervisor rejects) → REJECTED
PENDING_IT_SUPERVISOR → (IT Supervisor approves):
    ├── High-risk + tier → Section Head → Director → PENDING_COST_ESTIMATE
    ├── Tier2 or Internet-facing → Section Head → PENDING_COST_ESTIMATE
    └── Normal → PENDING_COST_ESTIMATE
PENDING_COST_ESTIMATE → (IT Staff submits estimate) → PENDING_DESIGN
PENDING_DESIGN → (IT Staff submits design) → PENDING_DEVELOPMENT
PENDING_DEVELOPMENT → (IT Staff marks complete) → PENDING_SIT_TEST_CASE
PENDING_SIT_TEST_CASE → (IT Supervisor approves test cases) → PENDING_SIT_EXECUTION
PENDING_SIT_EXECUTION → (2 SIT Testers submit results + IT Supervisor approves) → PENDING_UAT_TEST_CASE
PENDING_UAT_TEST_CASE → (IT Supervisor approves test cases) → PENDING_UAT_EXECUTION
PENDING_UAT_EXECUTION → (UAT Tester submits results + IT Supervisor approves) → PENDING_COMMITTEE
PENDING_COMMITTEE → (Committee approves) → PENDING_DEPLOYMENT
PENDING_DEPLOYMENT → (Deployment Executor completes) → PENDING_DEPLOYMENT_CHECK
PENDING_DEPLOYMENT_CHECK → (2 Checkers approve) → COMPLETED
COMPLETED → Notify: CR User "Your change request is complete"
```

## 6. Notification System

### 6.1 Email + In-App (both always)

Every state transition triggers notifications via Supabase Edge Function:

```
Trigger: IT Supervisor approves CR
Action:
  1. Update change_requests.status
  2. Insert into notifications (in_app + email for each recipient)
  3. Call Edge Function send_email() via SMTP
  4. Insert into cr_audit_log
```

### 6.2 Notification Rules (auto-triggered)

| Event | Recipients |
|---|---|
| New CR submitted | IT Team (it_staff role), Applicant's supervisor |
| CR approved by User Supervisor | IT Staff, IT Supervisor |
| CR needs Section Head approval | IT Section Head |
| CR needs Director approval | IT Director |
| CR approved by Section Head | IT Supervisor |
| CR approved by Director | IT Supervisor |
| CR rejected | Applicant, Applicant's supervisor |
| CR in SIT execution | Assigned SIT testers |
| CR in UAT execution | Assigned UAT tester |
| CR submitted to Committee | Committee members |
| CR approved by Committee | Deployment Executor |
| CR deployment completed | Applicant, Deployment Executor |
| CR completed | Applicant, Applicant's supervisor |
| @mention in Chatroom | Mentioned user(s) |

### 6.3 Per-CR Chatroom

Each CR has its own chatroom (messages table). @mention syntax:
- `@user@domain.com` → notify that user immediately via email + in-app
- `@it-staff` → notify all IT Staff role users

Chatroom UI shows:
- Chronological message thread
- @mentions highlighted with user link
- Notification sent to mentioned users

## 8. API Design (Supabase REST + Edge Functions)

### 8.1 REST Endpoints (Supabase auto-generated)

```
GET    /rest/change_requests          — List CRs (filtered by RBAC)
GET    /rest/change_requests/:id     — Get CR detail
POST   /rest/change_requests         — Create CR
PATCH  /rest/change_requests/:id     — Update CR (state transitions)
GET    /rest/cr_chat_messages?cr_id=  — Get CR chatroom messages
POST   /rest/cr_chat_messages        — Post message (triggers @mention logic)
GET    /rest/notifications?user_id=  — Get user notifications
```

### 8.2 Edge Functions (Custom Logic)

```
POST   /functions/v1/submit-cr        — Submit CR (state: draft → pending)
POST   /functions/v1/approve-cr      — Approve step (with approval routing logic)
POST   /functions/v1/reject-cr        — Reject CR with reason
POST   /functions/v1/advance-cr      — IT Staff advances to next step
POST   /functions/v1/add-note        — Add comment / @mention notification
POST   /functions/v1/send-email      — SMTP email sender
GET    /functions/v1/cr-dashboard    — Aggregated stats for dashboard
```

## 10. MVP Scope (Phase 1)

**Included:**
- ✅ User Submit CR with CR type + classification (tier, internet-facing, risk level)
- ✅ User Supervisor approve/reject
- ✅ IT Staff pickup and fill Impact Analysis
- ✅ Full approval routing tree (Supervisor → Section Head → Director) based on tier/risk
- ✅ IT Supervisor approve/reject (with routing logic)
- ✅ Cost Estimate step
- ✅ System Design step
- ✅ All RBAC roles + Role Management UI
- ✅ In-app + email notifications on every step transition
- ✅ Per-CR Chatroom with @mention
- ✅ Audit log
- ✅ Admin UI: CR Types config, Role assignment

**Excluded from Phase 1:**
- Development + SIT + UAT steps (stubbed as "future phase")
- Deployment steps (stubbed as "future phase")
- Committee review (stubbed as "future phase")
- File attachments (Phase 2)

**MVP Success Criteria:**
- A user can submit a CR
- It goes through the full approval chain (including conditional Section Head/Director)
- Notifications fire at each step
- Supervisor can reject and user sees the rejection
- IT roles can see all CRs; normal users see only their own
